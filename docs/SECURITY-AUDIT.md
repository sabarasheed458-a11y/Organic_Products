# Database and server-boundary security audit — 12 October 2026

Scope: all 25 public application tables, every foreign key and RLS policy, all existing six migrations, Storage policies, RPCs/helpers/triggers, 23 exported Server Actions, all four Route Handlers, request-scoped Supabase clients, Auth proxy, checkout, COD reconciliation, inventory, and public catalog reads. Two **additive, unapplied hosted migrations** implement the fixes below. Existing migrations and rows were not reset or rewritten. No service-role or secret API key is used; new guards reject those keys in the public-key setting without displaying their contents.

## Table, ownership and foreign-key inventory

All listed tables have RLS enabled. An active profile is required for private owner access and all staff authority. Public reads remain available without an account. UUID primary keys apply except inventory's variant key and store settings' singleton text key.

Eligibility arrays intentionally remain denormalized. Nonexistent UUID targets can become stale and make a coupon unusable; they do not grant purchases of unpublished products. Converting them to normalized FK join tables is a separate schema change. Review/order references intentionally block account deletion until a retention/anonymization workflow is followed. Inventory reserve columns exist, but this store deducts COD stock immediately; available = on hand − reserved. Returns restock the full inspected order, not partial/damaged returns.

## RPCs, triggers and request traces

- `staff_role`, `can_manage`: trusted active profile lookup; exposed read-only role helpers. No role is sourced from signup metadata.
- `new_profile`, `audit_change`, `immutable_snapshot`, `touch_product`, `prevent_variant_reparent`, `preserve_payment_identity`, `prevent_category_cycle`: trigger functions, not callable application endpoints. Auth signup always creates a customer profile/cart/wishlist. Mutation audits omit private profile contents.
- `consume_rate_limit`, `request_gate`, `checkout_internal`, `submit_inquiry_internal`: no anon/authenticated EXECUTE. Do not expose a private wrapper accidentally through future default grants.
- `checkout`: active authenticated customer, verified items/address, committed bounded gate, private atomic implementation. Authoritative DB prices → eligible locked coupon → ordered catalog/stock locks → immutable items → stock ledger → unpaid COD payment → redemption → cart clear. No browser total is accepted. Stable retries return the same order; failures retain only the throttle hit.
- `adjust_inventory`: catalog staff, explicit mode/nonnegative quantity/nonblank reason, row lock, nonnegative/reserved constraints, ledger movement.
- `transition_order`: order staff, locked order and allowed state graph, required shipment data, once-only stock restoration and timeline. Customers cannot call it to cancel another order.
- `record_cod_payment`: order staff; explicit real manual collection/refund, order lock, permitted payment/fulfillment state, atomic order/payment status and reasoned audit.
- `set_staff`: owner only, self-change forbidden, serialized role operations, trusted target UUID and role enum, before/after audit. Manager/catalog/order staff cannot promote themselves.
- `save_shopping`: active owner derived from JWT, shared shopping lock, bounded atomic replacement. Newly added entries must be published/active; already-owned archived entries may be retained so existing bags can still be corrected. No client-chosen owner ID.
- `order_timeline`: active owner or order staff only; customer details redacted.
- `duplicate_product`, `bulk_product_status`: catalog only; copies are draft with zero stock; bounded valid bulk input. Unique slugs/SKUs and stock/order FKs are retained.
- `asset_in_use`: catalog-only boolean; Storage uses it to protect shared references. `valid_store_configuration`: pure bounded boolean validator; it reveals no stored configuration or private records and may be executed to satisfy checks.

Public catalog repositories/`/api/catalog`/`/api/variants` use request-scoped publishable-key clients and explicit published/active filters, backed by RLS; no private identity/order/payment tables are included. The routes bound UUID lists, return generic errors and no-store responses. Customer order/confirmation/tracking queries also include `user_id=current user` even though RLS already isolates rows. Account addresses/profile and shopping mutations similarly derive the owner server-side.

The 20 commerce actions reviewed are `saveProduct`, `saveVariant`, `duplicateProduct`, `bulkStatus`, `editImage`, `deleteProduct`, `adjustStock`, `placeOrder`, `updateOrder`, `recordPayment`, `saveAddress`, `deleteAddress`, `saveProfile`, `sendInquiry`, `loadShopping`, `saveShopping`, `uploadImage`, `removeImage`, `saveRecord`, `updateStaff`. Each mutation validates a bounded schema and checks its owner/staff scope; generic table names use an own-property whitelist. Uploads validate MIME, size, magic bytes, alt/order fields and staff role before Storage insertion; metadata failure attempts object cleanup. Storage and SQL insertion are not one distributed transaction; orphan-object cleanup may still be needed after network failure.

The three auth actions are `authenticate`, `signOut`, `authDestination`. Native Auth verifies passwords/confirmation/session/PKCE; malformed modes are rejected, disabled profiles are logged out, errors are redacted, and return paths are constrained. `getUser()` is used for verified server identity; UI hiding is not the authorization boundary. Cookie refresh runs through the SSR proxy; authenticated responses are private/no-store. Next same-origin action checks were not disabled and no wildcard action origins were added.

The four Route Handlers reviewed: `GET /auth/callback` (PKCE exchange, constrained destination, generic failure), `GET /api/catalog` and `GET /api/variants` (bounded public reads), and `GET /api/admin/export` (settings staff, fixed financial columns, no addresses/phones, escaped CSV, no-store). CSV currently contains constrained references/statuses/numbers rather than arbitrary customer text. Online payment webhooks do not exist because no online provider is enabled; introducing one requires verified signatures/replay protection, not an unverified return-URL mutation.

## Migration plan and remaining decisions

1. Review [security-preflight.sql](../scripts/security-preflight.sql) in the trusted SQL editor. It prints only schema metadata and aggregate inconsistency counts. Check duplicate COD payment rows before the new unique constraint; the migration fails rather than deleting duplicates. Also review nullable eligibility arrays, banner dates, malformed settings, category cycles, stock-ledger discrepancies and public draft photos.
2. Deploy the Server Action changes **before** applying `202610120007_security_audit.sql`, because checkout/inquiry business failures now use `{error: ...}` payloads so their rate counters commit. The new Action code is backward compatible with the old exception contract. Use a maintenance window/staging first; replacing/renaming functions can wait for active transactions. Then apply `202610120008_configuration_integrity.sql`.
3. New NOT VALID checks enforce future changes without rewriting legacy rows. After reviewed corrections, explicitly VALIDATE `coupon_targets_not_null`, `banner_dates_valid`, `banner_link_internal`, and `store_configuration_valid`. Old catalog/order/payment/inventory rows and old idempotency hashes are preserved.
4. **Public-media privacy remains an architectural boundary.** Public bucket retrieval bypasses download RLS even for a known draft URL; old cached/public bytes cannot be made confidential retroactively. The admin uploader now states this. Keep confidential drafts out of the bucket; if private staging is required, use a separate private bucket and a reviewed publish/copy workflow. No existing public URLs were broken by this audit. [Supabase bucket behavior](https://supabase.com/docs/guides/storage/buckets/fundamentals).
5. **Anonymous contact still has a shared quota.** An attacker can exhaust it for all anonymous visitors. Implement visitor-aware trusted ingress limits/CAPTCHA and a securely authenticated server-to-DB rate identity before a busy public launch. Do not claim `x-real-ip` supplied directly to the public RPC is trustworthy. Native Auth calls made through SSR also share server-IP rate buckets unless a supported forwarding design is configured; this application deliberately does not introduce secret API keys to forward IPs. [Supabase Auth forwarding requirements](https://supabase.com/docs/guides/auth/rate-limits).
6. **Historical 001 uses schema-wide REVOKE statements.** Applying the initial migrations to a shared existing project can affect unrelated tables/functions. Use a dedicated project or capture/review its existing ACLs before initial installation; migration 007 cannot reconstruct unknown prior grants. Do not rerun 001 or reset production to obtain the new fixes.
7. No hosted credentials were supplied. Embedded PostgreSQL tests emulate Supabase Auth/Storage schemas and permissive default grants, and run as anon/two customers/owner/manager/catalog/order roles. They reproduce the old failures and check the new guards. They do not verify hosted JWT verification, email/SMTP delivery, native Storage byte validation, real gateway headers, independent-connection locking, or hosted default ACL drift. Run the existing live acceptance scenarios in staging using separate users and two simultaneous database connections before certifying production.

## Local verification

On 12 October 2026, all eight migrations executed successfully in the embedded PostgreSQL harness. The 39 database tests include 21 security regressions against both the original six-migration schema and the hardened schema, plus 18 commerce tests. All 28 unit tests, 27 production-browser tests across desktop/tablet/mobile, strict TypeScript checks, ESLint and the production build passed. Browser catalog fixtures are explicitly mocked where documented; they do not verify hosted catalog access. Access tests use actual database roles and emulated verified JWT claims, rather than bypassing RLS as the database owner. No hosted migration was applied and no service-role credential was requested or exposed.

Rollback/recovery: back up first and test restoration. If a new constraint fails, investigate its reported inconsistency; do not delete historical payments/orders/ledger entries or disable RLS. Prefer a follow-up corrective migration. Application code handles both old exceptions and new envelopes; rolling back the application first would misinterpret new envelopes. Do not grant anon/authenticated EXECUTE to the private implementation routines to “fix” a rollout.
